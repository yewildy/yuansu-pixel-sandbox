## 二、发现的缺陷

### 🔴 F01 · 致命 · 导热模型整体快了一个数量级，岩浆 0.08 秒凝固

**现象**：P6 场景——摆一摊岩浆，什么都不做。

**推演**：按 §6.1 原式 $T_i' = T_i + \alpha\sum \bar{k}(T_j - T_i)$，取原值 $\alpha = 0.12$、空气 $k = 0.05$、
岩浆 $k = 0.30$。岩浆与一个空气格的交换量：

$$0.12 \times \frac{0.30+0.05}{2} \times (20 - 1200) = -24.8\ ^\circ\text{C}/\text{tick}$$

岩浆四周通常有 3 个空气邻格 → **约 −99 °C/tick** → 从 1200 °C 掉到凝固点 700 °C **只需 5 tick ≈ 0.08 秒**。

**后果**：岩浆玩法整体失效——玩家还没看清，它已经全变成石头。同为受害者的还有冰、液氮、火焰（全部瞬间失温）。

**根因（两处叠加）**：
1. $\alpha$ 取 0.12 过大，把"稳固"当成了"灵敏"；
2. **空气 $k$ 取 0.05 严重高估** —— 真实空气导热系数 0.026 W/(m·K)，只有水的 1/23；首版设成水的 1/12。

**修复**：$\alpha: 0.12 \to \mathbf{0.005}$；空气 $k: 0.05 \to \mathbf{0.002}$。重算后岩浆 1200→700 °C 约 **2.2 秒**，而岩浆加热水仍需 **0.65 秒**（淬水依旧剧烈）。

---

### 🔴 F02 · 高 · 气体弛豫过快，蒸汽冒出来 0.1 秒就冷凝

**推演**：§6.3 原 `gas = 0.02`。蒸汽 110 °C 在空气中：$\Delta T = 0.02 \times (20-110) = -1.8$ °C/tick → **6 tick 掉到 100 °C 以下开始冷凝**。

**后果**：P1 场景里完全看不到上升的"蒸汽柱"，水火交互失去视觉反馈。

**修复**：`gas: 0.02 → 0.004`（约 4 秒寿命）。

---

### 🔴 F03 · 高 · 液体弛豫过大，岩浆 0.7 秒凝固（与 F01 同源）

**推演**：§6.3 原 `liquid = 0.005`，暴露加成 ×2 → `0.010`：$\Delta T = 0.010 \times (20-1200) = -11.8$ °C/tick → 500 °C 需 42 tick ≈ **0.7 秒**。

**修复**：`liquid: 0.005 → 0.0005`。固体/粉末同步从 `0.002 → 0.001`。

---

### 🟠 F04 · 高 · 相变被定义了两次，实现无法落地

**现象**：§6.4 说"平台停留累计超过 `LATENT_TICKS` 才切换物态"（**确定性**）；
§7 又说"每 tick 以概率 $p$ 判定"（**随机性**）。两者对同一件事给出不同机制。

**后果**：实现者只能二选一，要么失去潜热、要么失去随机感；且"水多久变蒸汽"会给出两个互相矛盾的答案。

**修复**：明确为**串联两道闸**（已写入 §6.4）：
① 能量闸 `latent ≥ LATENT_TICKS` → ② 随机闸 `rnd() < p(T)`，两闸同时通过才切换。
并补明钳温只在 $|T - T_{pc}| \le 2$ 窗口内生效；过热到窗口外（如 200 °C 的水）不再钳温、不吸潜热，纯按概率走（标注为**近似**）。

---

### 🟠 F05 · 中 · §9.1 点火条件自相矛盾

**现象**：条件 1 写了"（或该格自温 ≥ `ignitionTemp`）"，条件 3 却写"达标温度：命中 §9.2 的概率"——
可 §9.2 的概率 `flammability × 方向偏置` **根本不含温度**。于是"什么时候必燃、什么时候按概率"没有定义，
且 `ignitionTemp` 在燃烧链里成了死数据。

**修复**：拆清为三要素（可燃 / 邻接火源 / 有氧），并补一条**自燃特例**：$T \ge$ `ignitionTemp` 时 $p_{ign} = 1.0$。
于是 `flammability` = "接触火焰的引燃速度"，`ignitionTemp` = "自燃阈值"，两个属性各有明确语义。

---

### 🟠 F06 · 高 · 液氮在 −196 °C 就已经在沸腾，0.55 秒蒸发干净

**推演**：§7.8 原式 $p = 0.03 + 0.002(T+196)$，液氮初始温度正是 −196 °C → $p = 0.03$ → 平均 33 tick ≈ **0.55 秒全没了**。

**后果**：P5 场景里液氮毫无存在感，来不及冻结任何东西。

**修复**：改为纯斜率式 $p = \mathrm{clamp}(0.0005(T+196), 0, 0.5)$，在 −196 °C 时 $p = 0$。
液氮必须先被环境加热才汽化，寿命由弛豫主导（约 7 秒升到 −100 °C）。

## 五、教训（写进团队规矩）

1. **任何"输出温度/输出概率"必须代回守恒式或导热式验算一遍**，不能凭感觉写。F01 就是"看着合理、算出来差 100 倍"的典型。
2. **跨类元素（既是燃料又是爆炸物、既算湿度又算介质）必须在两处交叉引用**，否则一定出现规格矛盾。
3. **同一物理过程只能有一个机制**。发现两处都能解释同一件事时，必须合并成"串联闸"或"二选一"，不能并存。
4. **空气不是"随便填的介质"**：它的导热能力必须按真实比值压低，否则所有高温元素都会被空气瞬间抽干。

## 六、实现后复核（Phase 6.5 · 在真实引擎上跑）

设计稿冻结、代码写完之后，主理人**不依赖实现者自己的测试**，另起一套独立验证：直接 `require` core 模块在 Node 里跑场景，
以及用最小 DOM/Canvas 桩把浏览器入口整体跑起来。又发现 3 个问题，其中 1 个是**致命级**。

### 🔴 F15 · 致命 · 整数温度把「慢热过程」全部抹掉

**现象**：一片 −10 °C 的冰摆在 20 °C 空气里，跑 **3000 tick 温度纹丝不动卡在 −10**，永不融化。雪同理。

**根因**：
- `grid.temp` 用的是 `Int16Array`（整数 °C），写回时还做了四舍五入 `t[i] = (v + (v>=0?0.5:-0.5)) | 0`；
- 而冰每 tick 只升温：导热 +0.0227 °C、弛豫 +0.06 °C ≈ **+0.083 °C**；
- → 四舍五入回 −10，**每 tick 的 0.083 被永久丢弃**，永远累加不起来。

**影响面**：所有"慢"的热过程全废 —— 冰/雪融化、冷水被缓慢加热、热石头回温、烟慢慢冷却。
只有 ΔT 极大（岩浆淬水）的过程还能动，所以"看起来大部分是好的"，极具欺骗性。

**修复**：`temp` 改为 `Float32Array`，`commitTemp` 只做钳制、不再取整。内存代价 230 KB（可忽略）。
**实测结果**：冰在空气中 **2.25 秒**开始融化、**7.05 秒**化掉一半；雪 **1.35 秒**（应比冰快，符合设计）。

> **教训**：实现者最初把这条当成"刻意的性能取舍"，理由是"取整会让降温更快、破坏 §6.1 标定"。
> 它只想到了**降温侧**，没意识到**升温侧**的 <0.5 °C 增量同样会被丢掉 —— 而冰融化恰恰是升温侧。
> **任何"精度取舍"都必须双向验算：升温要算，降温也要算。**

### 🔴 F16 · 严重 · 我自己写错的回归判据（自查自纠）

R-01 原判据写成"岩浆在空气中 600 tick 后仍应是 LAVA"。但按 §6.1 标定，单格岩浆本来就该在 **2.2 秒**内越过凝固点 ——
**判据与设计意图自相矛盾**。已改为双向判据（既不许秒凝、也不许不凝）。

> **教训**：写回归判据时，必须**先回到设计目标**确认"期望值到底是多少"，不能凭直觉。

### 🟠 F17 · 中 · 模块依赖在"加载时"解析，顺序错即崩

各模块在顶层写 `var Balance = root.YS.Balance;`。在 Node 下若 `require` 顺序不对会直接抛
`Cannot read properties of undefined`。浏览器靠 `index.html` 的 script 顺序保证（已核对正确），
但 `tests/run.js` 与任何第三方引用都必须遵守同一顺序。

**处置**：在 `index.html` 与 `tests/run.js` 头部标注唯一权威的加载顺序；暂不改为惰性解析（改动面大、收益有限），
但**列入已知约束**。已核验 `index.html` 的 22 个 script 顺序与依赖关系完全一致。
