# ADR-0004 · 温度场改用浮点存储

| 字段 | 值 |

| 状态 | **已接受（Accepted）** |
| 日期 | 2026-09-24 |
| 取代 | [ADR-0001](0001-grid-and-memory-layout.md) 中关于「`temp` 用 `Int16Array` + 四舍五入回写」的决策 |

## 背景

ADR-0001 选择 `temp` 用 `Int16Array`（整数 °C）以节省内存，并让导热在 `Float32Array nextTemp`
里累加、回写时四舍五入。当时的论证只考虑了一个方向：**降温**。

它没有考虑**升温**。而这两者受同一把刀切。

## 问题

一片 −10 °C 的冰放在 20 °C 空气中，每个 tick 的升温是：

| 来源 | ΔT/tick |
|---|---|
| 与空气导热（k̄ = (0.30+0.002)/2 = 0.151，α = 0.005） | +0.0227 °C |
| 环境弛豫（固体 0.001，暴露 ×2） | +0.0600 °C |
| **合计** | **+0.083 °C** |

回写时 `(v + 0.5) | 0` 把这个 0.083 四舍五入回整数 −10。
**下一 tick 又从头开始算，于是这 0.083 被每 tick 永久丢弃，冰永远停在 −10 °C。**

实测（修复前）：

```
冰(-10C) 置于 20C 空气:
  tick 0    中心温度 = -10.00
  tick 3000 中心温度 = -10.00     ← 3000 tick 纹丝不动
```

受影响的**不只是冰**：一切"每 tick 变化量小于 0.5 °C"的过程全都被抹平 ——
雪融化、冷水被缓慢加热、热石头回温、烟慢慢冷却、蒸汽缓慢冷凝。
只有 ΔT 极大（岩浆淬水，几 °C/tick）的过程还能动，因此表面看起来"大部分功能是好的"，**极具欺骗性**。

## 决策

`grid.temp` 与 `grid.nextTemp` 都用 `Float32Array`；`commitTemp` 只做上下限钳制（−200 / 2000），**不再取整**。

```js
temp:     new Float32Array(n),
nextTemp: new Float32Array(n),

g.commitTemp = function (minT, maxT) {
  var t = this.temp, nt = this.nextTemp, n = this.n;
  for (var i = 0; i < n; i++) {
    var v = nt[i];
    if (v < minT) v = minT; else if (v > maxT) v = maxT;
    t[i] = v;              // ← 不取整
  }
};
```

## 代价

| 项 | 变化 |
|---|---|
| 内存 | `temp` 由 115 KB → **230 KB**（320×180），相对总量可忽略 |
| 存档体积 | JSON 里温度带小数，体积增大约 30%；如需可序列化时 `Math.round`（本版未做） |
| 确定性 | 不受影响（浮点运算在 V8 上确定；哈希测试仍通过） |

## 后果

- ✅ 冰在空气中 **2.25 s** 开始融化、**7.05 s** 融化过半；雪 **1.35 s**（快于冰，符合设计）
- ✅ 所有"慢热过程"恢复工作
- ✅ `tests/run.js` 新增 2 条回归：`9a 冰在空气中必须能融化`、`9b 温度场必须能承载亚度级增量`
- ⚠️ `docs/PHYSICS.md` §13.4 已同步为「温度场必须用浮点」

## 教训（写给未来的自己）

**任何"精度取舍"都必须双向验算：升温要算，降温也要算。**

ADR-0001 的论证写得头头是道，却只在降温一侧做了算术。
一个把 0.4 °C/tick 的降温放大成 1 °C 的方案，同时也会把 0.4 °C/tick 的升温压缩成 0 °C ——
而后者才是致命的。
