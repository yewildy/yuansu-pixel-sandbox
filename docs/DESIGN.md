## 1. Overview / Vision

### 1.1 一句话愿景
> **把一座物理实验室装进一个网页标签页**——玩家在 320×180 的像素沙盘上倾倒元素，观察它们遵循可预测、可解释的物理规则自行反应、燃烧、流动、生长。

Yuansu Pixel Sandbox 是一款**落沙物理沙盒（falling-sand physics sandbox）**，对标 Dan-Ball 的 Powder Game。它不是关卡制游戏，而是一套**可摆弄的物理玩具**：没有分数、没有失败、没有关卡；玩家的乐趣来自「设定初始条件 → 观察涌现结果 → 再试一次」的科学实验式循环。

### 1.2 设计目标（Project Goals）
| 目标 | 说明 | 可衡量标准 |
|---|---|---|
| **物理可解释** | 每条规则都是玩家能在脑中预演的因果（水灭火、火煮沸水、种子遇水发芽） | 规则可用一句中文说清，且写在 `PHYSICS.md` 的量化表里 |
| **量化优先** | 编码前先把每条规则量化（温度阈值、每 tick 概率、密度序） | `PHYSICS.md` 无「视情况而定」，全部为整数/浮点/概率 |
| **流畅** | 320×180 满网格在主流笔电上稳定 60 FPS | 见 §9 性能预算 |
| **即开即玩** | 单 HTML/JS 打开即可玩，零依赖、零构建 | 双击 index.html 可运行 |
| **中文优先 + 三语** | 默认简体中文，支持中/英/日无缝切换 | 见 §10 i18n 计划 |

### 1.3 非目标（Non-Goals，明确不做）
- **不做**多人在线、账号系统、后端服务（纯前端）。
- **不做**关卡/剧情战役/成就系统（沙盒玩具，非叙事游戏）。
- **不做**真实物理精度（流体用元胞近似，不用 Navier–Stokes）。
- **不做**移动端专属手势优化为 P0（响应式可用即可，触控为 v1.0 增补）。
- **不做**用户自定义元素脚本（Backlog 再议，避免沙盒越狱与性能失控）。

### 1.4 玩家画像（Target Player）
- **主目标**：喜欢「玩弄系统」的玩家——Sandbox / Powder Game / The Powder Toy / Noita 玩家，Bartle 类型以 **Explorer（探索者）** 为主，其次 **Tinkerer/成就型**（追求搭建复杂机关）。
- **场景**：5–30 分钟碎片时间；打开网页随手玩，用于「放空 + 好奇心满足」。
- **心理收益**：掌控感、发现感、可分享的「我搭了个什么」的创造快感。

## 2. Design Pillars（设计支柱）

> 支柱是**取舍裁判**：任何设计争议，先问「它是否服务于某条支柱」。支柱不超过 4 条。

### 支柱 1 — **物理诚实（Physics You Can Predict）**
规则必须**可预测、可解释、可复现**。玩家应当能学会「往火上倒水会冒蒸汽」并信任这条规则每次都成立。
- **取舍含义**：宁可牺牲真实感，也要保证**因果清晰**。例：水在 100°C 才蒸发（而不是随时缓慢蒸发），因为玩家需要一条清晰的心智模型。
- **反例警戒**：加入随机混沌导致「同样操作不同结果」会直接破坏本支柱。

### 支柱 2 — **涌现即乐趣（Emergence Over Content）**
我们**不设计内容，我们设计规则**。乐趣来自规则之间组合出的、设计者未曾预设的结果（岩浆+酸+克隆重=无限炼狱）。
- **取舍含义**：优先做**相互作用丰富**的元素，而不是**数量多但互不作用**的元素。30 种元素必须两两有意义的交叉反应。
- **反例警戒**：加入一个「不与任何元素反应」的元素是浪费预算。

### 支柱 3 — **一眼可读（Readable at a Glance）**
玩家必须能在**不做任何操作**的一帧里，仅凭颜色/形态/动势读懂画面状态（哪里在烧、哪里在流、哪里在长）。
- **取舍含义**：视觉清晰度优先于视觉华丽（详见 `ART.md`）。温度、状态需有**可选可视层**（热力图叠加）而非常显。
- **反例警戒**：全屏噪点、UI 抢焦点都会破坏可读性。

### 支柱 4 — **零摩擦进入（Zero-Friction Entry）**
打开即玩、无需注册、无需教程即可上手；但**对愿意深挖的玩家保留深度**（可调参数、热力图、单步调试）。
- **取舍含义**：默认界面极简（几个工具 + 元素板），高级功能收进「设置/调试」。
- **反例警戒**：上来就弹出长教程、多级菜单，会劝退 Explorer。

## 3. MDA 分析（Mechanics → Dynamics → Aesthetics）

> 采用 Hunicke/LeBlanc/Zubek 的 MDA 框架：**设计者从 M 出发，玩家从 A 反向感知。**

### 3.1 Mechanics（机制，设计者构建的规则与数据）
本作的机制恒等于**元胞自动机的物理规则集**，不含「关卡机制」。核心机制清单：

| 机制族 | 内容 | 真源 |
|---|---|---|
| M1 物质态移动 | 粉末坍塌、液体扩散、气体浮力+扩散、静态不动 | `PHYSICS.md` §5 |
| M2 热传导 | 离散导热 + 向环境温度弛豫 | `PHYSICS.md` §6 |
| M3 相变 | 熔/沸/凝/固，含每 tick 概率 | `PHYSICS.md` §7 |
| M4 化学反应 | 燃烧、溶解、爆炸、腐蚀、复制 | `PHYSICS.md` §8 |
| M5 生命/植物 | 种子发芽、植物蔓延、病毒复制 | `PHYSICS.md` §10 |
| M6 气流 | 全局风场 + 热对流平流 | `PHYSICS.md` §11 |
| M7 玩家输入 | 画笔、元素选择、风力、暂停/单步 | 本文 §8 |

### 3.2 Dynamics（动态，机制运行时涌现的行为）
单条机制无趣，机制**组合**才产生动态：

| Dynamic | 涉及的 Mechanics | 玩家可观察现象 |
|---|---|---|
| D1 火水对抗 | M2+M3+M4 | 水浇火→冒蒸汽；火煮水→沸腾；火在水面熄灭 |
| D2 元素循环 | M3+M4 | 岩浆冷却成石、石头被加热再融成岩浆（闭环） |
| D3 燃烧链式反应 | M2+M4+M6 | 火沿木材/油气向上蔓延，被风改变方向 |
| D4 植物生态 | M5+M3+M2 | 种子遇水发芽→长成植物→被烧成灰 |
| D5 腐蚀/炼金 | M4 | 酸蚀金属→产气；岩浆+冰→石+水 |
| D6 复制失控 | M4 | 克隆体复制任意邻格、水源泉无限出水（须被规则约束） |
| D7 风塑形 | M6+M1 | 风吹烟/蒸汽呈流线，风吹散种子 |

### 3.3 Aesthetics（美学，玩家感受到的情绪体验）
按 MDA 的 8 类美学（LeBlanc）映射，本作**主攻前 3 项**：

| 美学 | 强度 | 说明 |
|---|---|---|
| **Discovery 发现** | ★★★★★ | 主美学。「如果我把 X 放到 Y 上会怎样？」的持续驱动力 |
| **Sensation 感官** | ★★★★☆ | 副美学。发光、流动、颗粒抖动带来的视觉愉悦（见 `ART.md`） |
| **Challenge 挑战** | ★★★☆☆ | 隐性挑战：搭建稳定机关、控制反应规模（无强制目标） |
| **Expression 表达** | ★★★☆☆ | 自由搭建 = 自我表达（可分享截图，v1.0） |
| Fantasy 幻想 | ★★☆☆☆ | 弱：实验室/炼金隐喻，无强叙事 |
| Narrative 叙事 | ★☆☆☆☆ | 极弱：无剧情（非目标） |
| Fellowship 社交 | ★☆☆☆☆ | 弱：无联机（非目标） |
| Submission 消磨 | ★★☆☆☆ | 弱：可放空玩弄，但非挂机游戏 |

**设计意涵**：核心资源应投在 **Discovery + Sensation** 上——即「更多有意义的元素交互」+「更清晰愉悦的视觉反馈」，而不是投在关卡或叙事上。

## 4. 玩家动机（自我决定论 Self-Determination Theory）

以 Deci & Ryan 的三大基本心理需求映射设计：

| 需求 | 在本作中的体现 | 具体设计手段 |
|---|---|---|
| **自主 Autonomy** | 无目标、无强制路径，玩家完全决定玩什么 | 空白沙盘 + 全部元素即刻可用（不解锁）；可调参数（风力、画笔、温度显示开关）；可选调试面板 |
| **胜任 Competence** | 「我理解了这个系统」的掌控感与熟练感 | 规则可预测（支柱 1）；物理规则随操作即时反馈；进阶玩法（连续反应链、稳定机关）提供成长曲线 |
| **关联 Relatedness** | 沙盒游戏的关联较弱，靠「与系统对话」与「分享作品」补足 | 拟人化元素命名（种子「发芽」、病毒「感染」）；v1.0 提供存档分享码/截图导出，形成「给朋友看我搭的东西」 |

**动机补充（Bartle）**：
- **Explorer**：主要受众 → 靠元素交叉反应的广度喂养。
- **Achiever**：次要受众 → 靠「搭出复杂/稳定机关」的自设目标喂养（v1.0 存档系统服务此）。
- **Killer/Socializer**：非重点受众（无对抗/无社区）。

## 5. 范围分层（Scope Tiers）

> 原则：MVP 必须可玩且物理完整；v1.0 补体验与持久化；Backlog 是「如果还有时间」的清单。**MVP 边界内不做任何占位符**。

### 5.1 MVP（可发布的最小完整体验）
- 320×180 网格 + 60 tick/s 固定步长仿真引擎（core 与 DOM 解耦，可在 Node 跑单测）。
- **全部 30 种元素**（清单见 §6）及其核心交互（移动/相变/燃烧/溶解/爆炸/发芽）。
- 温度场（int16/格）+ 热传导 + 相变 + 环境弛豫。
- 全局风场（方向+强度）+ 气体平流。
- 画笔（尺寸 1/3/5/9）+ 元素面板 + 橡皮擦 + 吸管。
- 模拟控制：暂停 / 单步 / 清屏 / 复位风速。
- 渲染：Canvas2D + ImageData 像素直写，1 格 = 1 像素，整数倍放大，最近邻（见 `ART.md`）。
- 简体中文 UI（中文优先）。

**MVP 验收**：用户能在空白画布上完成「倒水→点火→加热→见蒸汽→冷凝成雨」的完整链条，且帧率 ≥ 60 FPS。

### 5.2 v1.0（体验与持久化完善）
- 中/英/日三语切换（实时，无需刷新）。
- 温度热力图叠加显示（可选层）+ 单格温度数值读数（悬停）。
- 存档 / 读档：网格序列化为可压缩字符串（localStorage）+ 分享码（base64）。
- 温度显示 / 网格线 / 色盲纹样 / 高对比 / 减少动效等设置项（对齐 `ART.md` §4）。
- 截图导出 PNG。
- 触控支持（指针事件统一鼠标/触摸）。
- 风力工具 UI（方向罗盘 + 强度滑杆）。
- 性能：自适应质量降级（帧率不足时降仿真子步）。

### 5.3 Backlog（愿景 / 时间允许再做）
- 「光源/光」模型（让种子发芽真正依赖光 → 影响发芽规则，见 `PHYSICS.md` §10 的「近似光」方案）。
- 更多元素（如 电/导线、玻璃熔炼链增强）。
- 预设场景库（「火山岛」「下雨的森林」一键载入）。
- 时序录制/回放（把一次实验录成动画）。
- 自定义调色（玩家改元素色，仅本地）。
- WebGL 后端渲染（仅在 Canvas2D 性能触顶时考虑，属技术重估项）。

## 6. 核心游戏循环（Core Loop）

本作是**沙盒**，循环不是「目标-奖励」，而是**实验循环**：

```
        ┌─────────────────────────────────────────────┐
        │                                             │
        ▼                                             │
  [1] 观察 Observe ──► [2] 假设 Hypothesize ──► [3] 操作 Act
   读画面当前状态         "如果…会怎样?"            画笔倾注元素/调风
        ▲                                             │
        │                                             ▼
  [6] 再试 Retry ◄── [5] 反思 Reflect ◄── [4] 反馈 Feedback
   改条件重来            形成/修正心智模型         物理即时演算结果
```

**逐环节设计要点**：
1. **观察**：画面即状态；温度/危险靠自发光与热力图可视化（支柱 3）。
2. **假设**：玩家自发提出「火+火药会爆吗」——无需系统提示，靠规则一致性诱发。
3. **操作**：< 100ms 内看到反馈（性能预算 §9），操作手感即乐趣来源。
4. **反馈**：物理规则确定、及时、可解释（支柱 1）。
5. **反思**：现象可归因（「因为没空气所以没烧起来」）。
6. **再试**：清屏/单步/撤销（撤销为 Backlog）降低重试成本。

**Session 结构（一次典型游玩）**：
- 0–30s：随意倾倒，探索基础反应（水/沙/火）。
- 30s–5min：刻意组合元素，追求特定现象（做火山、做雨、做玻璃）。
- 5–30min：搭建半稳定机关，微调参数（风力、连续反应）。
- 退出点：现象达成或好奇耗尽——**设计要求：任何时刻都可安全关闭，无需存档也能重来**（Backlog 存档提升留存但不阻塞）。

## 7. 元素总表（30 种）

> 与 `ART.md` §2.1 的 ID、类别、配色**严格一致**（ID 即 colorIndex）。物理数值见 `PHYSICS.md` §4。

| ID | 中文名 | 英文名 | 类别 | 一句话行为 |
|---|---|---|---|---|
| 1 | 空 | EMPTY | special | 空气/占位：近乎真空的介质，参与散热与燃烧供氧，可被气体压入 |
| 2 | 墙 | WALL | static | 不可破坏的固定边界，隔绝一切，仅用于围栏与结构 |
| 3 | 岩石 | STONE | static | 静态固体，可被强酸缓慢腐蚀，高温熔为岩浆 |
| 4 | 玻璃 | GLASS | static | 半透明静态固体，酸不蚀，高温熔为岩浆 |
| 5 | 金属 | METAL | static | 高导热固体，导热极快，可被强酸腐蚀生成瓦斯 |
| 6 | 冰 | ICE | static | 0°C 以上融化，吸收大量热，融化变水 |
| 7 | 木材 | WOOD | static | 可燃固体，燃点 300°C，烧后成灰 |
| 8 | 植物 | PLANT | special | 生命体：遇水/土壤向上生长蔓延，可燃，可被病毒感染 |
| 9 | 沙 | SAND | powder | 典型粉末，堆积成丘有休止角，高温融为玻璃 |
| 10 | 土壤 | SOIL | powder | 粉末且富肥力，可供种子发芽，可燃性极低 |
| 11 | 盐 | SALT | powder | 粉末，遇水溶解，高温熔融 |
| 12 | 尘埃 | DUST | powder | 轻质粉末，易被风吹动，可燃性微弱 |
| 13 | 雪 | SNOW | powder | 极轻粉末，0°C 以上融化为水，堆积松散 |
| 14 | 灰烬 | ASH | powder | 燃烧残余，轻质粉末，可被风吹散 |
| 15 | 煤 | COAL | static | 可燃固体，燃点 400°C，耐烧、放热高 |
| 16 | 火药 | GUNPOWDER | powder | 粉末，遇火/高温速燃并向四周爆燃 |
| 17 | 种子 | SEED | powder | 生命起点：满足湿度/温度/暴露条件后发芽成植物 |
| 18 | 水 | WATER | liquid | 主液体：流动、导热、灭火、100°C 沸腾成蒸汽 |
| 19 | 油 | OIL | liquid | 轻于水（浮于水面），可燃液体，燃点 250°C |
| 20 | 岩浆 | LAVA | liquid | 高温发光液体，遇水速固为石并产蒸汽，冷却凝固 |
| 21 | 强酸 | ACID | liquid | 腐蚀性液体，溶解金属/岩石，向下渗蚀 |
| 22 | 液氮 | LN2 | liquid | 超低温液体（-196°C），急速制冷，气化为冷蒸汽 |
| 23 | 水蒸气 | STEAM | gas | 气态水：上升、被风吹散，降温冷凝回水 |
| 24 | 烟 | SMOKE | gas | 燃烧副产气体，上升、随风飘散，逐渐消散 |
| 25 | 火 | FIRE | gas | 燃烧的能量态：放热、向上蔓延、需燃料与氧维持 |
| 26 | 瓦斯 | GAS | gas | 甲烷气体：上升、易燃易爆（燃点 540°C） |
| 27 | 克隆体 | CLONE | special | 复制机：将相邻格复制成目标元素（受规则约束制造质量） |
| 28 | 病毒 | VIRUS | special | 传染体：感染生物质（植物/木材）将其转为病毒 |
| 29 | 水源泉 | SPRING | liquid | 无限水源：持续向相邻空位产出水（受配额约束） |
| 30 | 炸药 | TNT | special | 静态炸药块：受高温/火焰/爆炸触发剧烈大范围爆炸 |

**类别分布**：静态固体 6（WALL/STONE/GLASS/METAL/ICE/WOOD/COAL 中的静态项，含特殊静态）、粉末 9、液体 6、气体 4、特殊 5——合计 30。所有元素**均参与至少一条跨类反应**（满足支柱 2）。

## 8. UX 设计

> 目标：**界面隐形**（见 `ART.md` §1）。默认只暴露「画画需要的」，高级功能收进「设置/调试」。

### 8.1 整体布局（Landscape 优先）
```
┌───────────────────────────────────────────────────────────┐
```

### 8.3 元素面板（Element Palette）
- 30 个**网格按钮**，每格 = 元素色块（`base` 色）+ 选中外环 `accent`。
- **分组**：静态固体 / 粉末 / 液体 / 气体 / 特殊（5 组，可折叠）。
- **Tooltip**：悬停显示「中文名 · English · 类别」。
- **视觉**：选中项底 `selected #2A3852` + 左侧 `accent` 竖条（`ART.md` §3）。
- **键盘**：`1–9` 快速选前 9 个常用元素；Tab 可聚焦全部。

### 8.4 温度显示（Temperature Display）
- **默认**：不显示数字，仅靠元素自发光（岩浆/火）传达「热」。
- **可选开关**（设置）：**热力图叠加层**——把每格温度映射为色带（冷蓝 → 中性透明 → 热红/白），半透明叠加在画布上。
  - 映射（可调）：`t=-200°C → #1E6FB8`，`t=20°C → 透明`，`t=100°C → #FFB020`，`t≥600°C → #FFFFFF`。
- **悬停读数**（v1.0）：鼠标悬停时右下角显示 `(x, y) 元素名 · 温度 °C · 寿命`，等宽字体（`ART.md` §5.1）。

### 8.5 风力控制（Wind Control）
- **风力工具**：点击进入后，在画布上**从起点拖到终点**定义一个向量箭头。
- **快捷条**：方向罗盘（8 向 + 任意角）+ 强度滑杆 `0.0–1.0`。
- **视觉**：画布边缘显示淡色箭头指示当前风（不遮挡内容）。
- **复位**：`Reset Wind` 按钮回到无风。
- **物理耦合**：见 `PHYSICS.md` §11（风主要影响气体与轻质粉末）。

### 8.6 模拟控制（Simulation Control）
| 控件 | 行为 | 快捷键 |
|---|---|---|
| 暂停/播放 | 冻结/恢复 tick 推进 | `Space` |
| 单步 | 推进 1 tick（仅暂停态） | `.` |
| 清屏 | 全清 + 复位温度/风 | `Ctrl+Del` |
| 复位风 | 风归零 | — |
| 调速（可选） | 0.5× / 1× / 2× tick 倍率 | `-` `=` |

### 8.7 存档/读档（Save/Load，v1.0）
- **快照格式**：`{version, w, h, element: Uint8[], temp: Int16[], age: Uint16[], wind:{x,y,s}}`。
- **存储**：`localStorage`（key: `yuansu.save.<slot>`），多槽位（1–4）。
- **分享码**：整个快照经 Run-Length Encoding + Base64 → 一段可复制文本。
- **兼容**：`version` 字段做迁移；不兼容时提示而非静默失败。

### 8.8 输入处理原则
- **指针事件统一**：用 `pointerdown/move/up` 同时覆盖鼠标与触控。
- **焦点**：全部控件可 Tab 聚焦、Enter/Space 激活（`ART.md` §4.4）。
- **触控目标** ≥ 44×44 CSS px；桌面按钮 ≥ 32×32 px（`ART.md` §4.3）。
- **可访问性**：提供色盲纹样、高对比、减少动效开关；不单独依赖颜色表意。

## 9. 性能预算（Performance Budget）

### 9.1 帧预算（目标 60 FPS = 16.67 ms/帧）
| 阶段 | 预算 | 说明 |
|---|---|---|
| 输入处理 | ≤ 0.5 ms | 指针事件驱动，无轮询 |
| 仿真 tick | ≤ 6.0 ms | 320×180 = 57,600 格；SoA 类型化数组 |
| 渲染（ImageData 直写 + blit） | ≤ 6.0 ms | 57,600 px × RGBA = 230 KB/帧 |
| UI/DOM 更新 | ≤ 1.5 ms | 仅在状态变化时更新 DOM |
| 余量 Headroom | ≥ 2.5 ms | 应对 GC 与浏览器抖动 |
| **合计** | **≤ 16.67 ms** | — |

### 9.2 数据结构（性能关键）
- **Structure-of-Arrays（SoA）**，避免对象数组：
  - `Uint8Array element[57600]`
  - `Int16Array temp[57600]`
  - `Uint16Array age[57600]`
  - `Uint8Array flags[57600]`（bit0 = 本帧已移动，bit1 = 本帧已反应）
- **双缓冲**：`temp` 与 `nextTemp` 交换，避免读写冲突。
- **零 GC**：主循环内不 `new` 对象/数组/闭包；复用临时变量。

### 9.3 优化手段
| 手段 | 收益 |
|---|---|
| EMPTY 快速跳过 | 空旷画布几乎零仿真成本 |
| 脏矩形渲染（v1.0 可选） | 静止画面只重绘变化区 |
| 扫描方向逐帧交替 | 消除方向偏置，无需额外成本 |
| 温度场惰性更新 | 温度全为环境值（20°C）时跳过导热 |
| 自适应降级 | 帧率 < 55 FPS 时降子步/降热力图刷新率 |

### 9.4 复杂度估算
- 单 tick 主循环 ≈ 57,600 × ~40–60 次简单整数/浮点操作 ≈ **2.3–3.5 M ops/tick**。
- 60 tick/s → **~140–210 M ops/s**。现代 JS 引擎（JIT + 类型化数组）可承载，属「可行但需优化」区间——因此**必须**用 SoA + 类型化数组 + EMPTY 跳过。

### 9.5 内存
- 每格：1B(element) + 2B(temp) + 2B(age) + 1B(flags) = **6 B/格**。
- 网格 ≈ 345 KB；双缓冲温度 + 渲染 ImageData ≈ 再 0.5 MB。总计 < 2 MB，可忽略。

## 10. i18n 计划（中 / 英 / 日）

### 10.1 原则
- **中文优先**：默认 `zh-CN`，UI 文案先写中文再翻译。
- **零依赖**：不引入 i18n 库；自建轻量字典 + `t(key)`。
- **无 FOUC**：语言包内联或首帧前加载；切换语言不刷新页面。

### 10.2 语言检测与切换

## 11. 风险清单（Risk Register）

> 分级：P = 概率（低/中/高），I = 影响（低/中/高）。

| # | 风险 | P | I | 说明 | 缓解措施 |
|---|---|---|---|---|---|
| R1 | **物理调参失衡**（主导策略/经济失衡） | 高 | 高 | 某组合过强（如无成本无限克隆/水源）使其它元素无意义 | 守恒规则（`PHYSICS.md` §13）；克隆/源泉配额上限；发布前跑「作弊组合」检查表 |
| R2 | **性能不达标**（移动端/低端机掉帧） | 中 | 高 | 满屏复杂反应时 60 FPS 失守 | 性能预算（§9）；SoA + EMPTY 跳过；自适应降级；提供「低画质」档 |
| R3 | **认知过载**（30 元素 + 反应复杂） | 中 | 中 | 新玩家不知从何下手 | 元素分 5 组；前 9 常用元素数字快捷键；规则可预测（支柱1）；不强制教程 |
| R4 | **相变/温度混沌导致不可复现** | 中 | 高 | 随机概率过大时同样操作结果不同，破坏支柱1 | 概率经校准（`PHYSICS.md` §7）；关键反应确定性优先；**支持固定随机种子** |
| R5 | **质量守恒被破坏**（Clone/Spring/相变产气） | 中 | 中 | 无限产物质导致画面爆炸 | 明确例外规则 + 全局格预算上限（`PHYSICS.md` §13） |
| R6 | **浏览器差异**（ImageData 颜色/Safari 性能） | 低 | 中 | 像素渲染/颜色在不同内核下不一致 | 只用标准 Canvas2D API；规避已知 Safari ImageData 陷阱；跨浏览器冒烟测试 |
| R7 | **跨文档不一致**（元素 ID/名/数值漂移） | 中 | 中 | ART/PHYSICS/DESIGN 三方对不上 | 以 `ART.md` 为视觉真源、`PHYSICS.md` 为物理真源；改 ID 必须三方同步；评审用 Grep 校验 |
| R8 | **无障碍不达标** | 低 | 中 | 色盲/光敏/键盘用户不可用 | 遵循 `ART.md` §4（明度阶梯、纹样、≤5Hz、焦点环、44px） |
| R9 | **范围蔓延**（想加更多元素/光源/联机） | 高 | 中 | 拖慢 MVP 交付 | 严格 MVP 边界（§5.1）；新想法进 Backlog；少即是多（支柱2 优先交互深度） |
| R10 | **无光模型导致发芽规则不自然** | 中 | 低 | 用户预期「植物需要光」 | MVP 用「暴露度（上方 2 格有 EMPTY/WATER）」近似光条件；光模型列入 Backlog；文档显式标注 |

### 11.1 设计理论红线（自查清单）
- ❌ **主导策略**：是否存在「一个元素/组合明显优于所有其它」？→ 检查克隆/源泉/无限连锁，配额约束。
- ❌ **经济失衡**：质量/温度是否被无偿放大？→ 守恒 + 环境弛豫吸收。
- ❌ **认知过载**：一屏同时最多让玩家处理多少状态？→ 默认隐藏温度层、UI 隐形。
- ❌ **支柱漂移**：新增功能是否仍服务 4 支柱？→ 每项 Backlog 提案须对齐支柱。

## 12. 待用户拍板项（Open Questions）

1. **默认放大倍率**：`4×（1280×720）` vs 「自动取最大整数倍」——建议后者（同 `ART.md` 待议项）。
2. **是否引入光模型**：MVP 用「暴露度」近似 vs 直接做光源元素（成本更高）。影响 `PHYSICS.md` §10 发芽规则。
3. **调速功能是否进 MVP**：0.5×/2× 对观察慢反应有用，但增加 UI 复杂度。
4. **随机种子是否暴露给玩家**：影响 R4 的可复现性与「实验室」调性。
5. **清屏是否需要二次确认**：防误触 vs 打断流畅性（建议：首次确认，可在设置关闭）。
