## 2. V38 —— 物理诚实性（**当前红，必须修**）

**判据**：走廊内所有被判为 STEAM 的格子，温度 **≥100 °C**，且低于 100 °C 的占比 ≤5%。

**当前实测**：走廊 701 格蒸汽，温度 min **99.90** / 中位 **99.90** / max **99.95** °C，
**低于 100 °C 的占 100%**。

**根因**（`src/core/transitions.js`）：`if (Air.flueCell(i)) { if (lat[i]===0) lat[i]=1; }`
—— 烟道内潜热预算被强制续命，蒸汽永远不凝结，于是"37~100 °C 的汽"也能一直算数。

**修的时候注意**：这条不是"调个阈值让它绿"。真实物理里 100 °C 以下的水蒸气就是水。
正确的方向是让**输运本身**成立（保温 / 更高的供汽温度 / 更短路径 / 更大流量），
而不是把凝结关掉。修完必须同时看：

- V38 转绿
- V37 仍然绿（别为了保温把汽弄成和石壁一个色）
- V39 仍然绿（plug 烟塞还得走得动）
- **V24 / V25 / V32 不许有任何变化**（它们是无烟道场景，见 §7）

## 3. V37 —— 像素级可见性（历史事故，别重演）

**判据**（两遍：默认视图 `showHeat=false` + 热力图 `showHeat=true`，各自带零对照臂）：

| # | 判据 | 门槛 | 当前 |
|---|---|---|---|
| **A** | 蒸汽亮度**均值** − 石壁基准，**有符号**（只准汽更亮） | **≥ +40/255** | +94.6 ✅ |
| A2 | 走廊蒸汽里"显著亮于石壁"的比例 | ≥60% | 100% ✅ |
| A3 | 六条腿**每条**"显著亮于石壁"的像素数（纯像素口径） | ≥20 | 53/80/79/84/84/161 ✅ |
| **B** | 走廊内**全部**像素均亮 − **紧贴**石壁（左右各 2 格）均亮 | **≥ +40/255** | **−92 ✗** |
| B2 | 零对照臂（腿1~5）不得满足判据 B | < +40 | −109…−106 ✅ |
| A4 | 零对照臂：腿1~5 亮点 ≤2、远端走廊亮点 ≤8 | | 0 / 0 ✅ |
| A5 | 开烟道远端亮点 ≥ 关烟道 ×4 + 20 | | 540 vs 0 ✅ |

**判据 B 为什么单独存在**：A 只判"**每一格汽**够不够亮"，判不了"**整条管道**看起来像什么"。
B 取走廊全域均值 vs 紧贴石壁均值，同时抓两种相反的失败：
- 汽太少/太稀 ⇒ 走廊是近黑背景，均亮**低于**石壁 ⇒ 判"没通"（当前就是这个状态）；
- 汽糊成一片 ⇒ 走廊和墙一个亮度，迷宫结构整片消失 ⇒ 判"不可见"（历史事故就是这种）。

**当前判据 B 红，且不是调色板能救的**：走廊均亮 31~72，石壁均亮 123~126，差 −92…−54。
管道里要么是汽（亮度 226）要么是空气（15），要抬到 ≥163 需要**截面填充率 ≈70%**
（现在 8%~24%）。**这是输送量问题，不是画法问题。** 改调色板救不了它。

**历史事故（v1.6.10，被用户当面驳回）**：蒸汽调色板 `alpha=0.5` 把亮度压到 122，
石壁 125，**只差 1.1%**，5%~95% 亮度区间重叠 43.8%。
引擎里数出 654 格蒸汽，截图上是同一个灰度 —— 用户一句"你自己看看有蒸汽过吗"。

**判据有牙的证据**（可复跑）：`node _probe_qa_mutate.js`

## 4. V39 —— plug 一次性注入（因果性，防假阳性）

**判据**：
- 开烟道：一次性烟塞走过的腿 **≥5 条**，且**必须到达出口腿（腿1）**，每腿峰值 ≥8 格；
- 关烟道：腿1~5 峰值 **≤2**（烟塞必须被困在腿6），且末态走廊蒸汽 **≤16**（证明凝结还活着）。

**当前实测**：开 `22/22/22/22/22/64`（命中 6/6，末态 0——全部从开口出去了）；
关 `0/0/0/0/0/64`（命中 1/6，末态 1）。

**踩过的坑（务必别再踩）**：上一版主判据用**持续注入（cont）**，注入时自带 heat
⇒ 即使关掉加热，注入本身也在推着气体走 ⇒ **对照组也在流** ⇒ 假阳性。
正确口径是 **plug（一次性注入）**：注完就断源，只有烟道抽力能让它动。

## 5. V40 + §7 无烟道场景零影响（回归护栏）

**V40 判据**：开放场景（无窄通道）跑 400 tick：
- `Air.flueLaneCount()` 累计 **= 0**
- `Air.flueMoved()` 累计 **= 0**
- 与 `FLUE_P_MAX=0` 臂**逐格完全一致**（差异 = 0 格）

**历史事故**（`docs/FLUE-THROUGHFLOW.md` §3.1）：几何判据把烧水锅上方的**上升羽流**
也认成烟道 ⇒ FLUE 在锅上方架起隐形输送带 ⇒ V25 余水 127 → 110，跌破 30% 门槛。
**现在这条已经数值化守护。**

另外这些**无烟道场景的测试必须逐字不变**，它们任何一个变了都说明 FLUE 泄漏了副作用：

## 6. 性能

```bash
node -e "
var p=require('path');
['balance','rng','elements','grid','thermal','transitions','reactions','movement','air','biology','wind','waves','pressure','engine'].forEach(function(m){require(p.join(process.cwd(),'src','core',m+'.js'))});
require(p.join(process.cwd(),'src','render','palette.js'));
var YS=globalThis.YS,S=require('./_serp5.js');
function bench(off){YS.Balance.AIR.FLUE_P_MAX=off?0:1.0;var e=S.build();
  for(var i=0;i<200;i++)e.step();var t=Date.now();for(var k=0;k<600;k++)e.step();return (Date.now()-t)/600;}
var on=bench(false),of=bench(true);
console.log('烟道开 '+on.toFixed(3)+' / 烟道关 '+of.toFixed(3)+' / FLUE 增量 '+(on-of).toFixed(3)+' ms/tick');
"
```

**基线（2026-10-23 实测）**：

| | ms/tick | 说明 |
|---|---|---|
| 烟道开 | 6.99 | 整场景仿真（含蒸汽/水/传热） |
| 烟道关 | 6.80 | 同上，只是关掉 FLUE |
| **FLUE 增量** | **+0.19（+3%）** | 这才是烟道机制的代价 |

**门槛**：
- **FLUE 增量 ≤ 1.0 ms/tick**（现 0.19，有 5 倍余量）
- 场景总耗时 ≤ 8 ms/tick（现 6.99；60 fps 预算 16.7 ms，仿真约占 42%）

> 注意：总耗时的**大头不是烟道**。如果总耗时突然涨而 FLUE 增量没涨，
> 去查传热/蒸汽量，别冤枉 flueFlow。
> 如果 FLUE 增量涨到 >1 ms，先查 `FLUE_ANALYZE_INTERVAL` 是否被改成 1、
> 几何分析是否每帧都跑（`_flueForce` 没复位）、车道数是否炸了。
