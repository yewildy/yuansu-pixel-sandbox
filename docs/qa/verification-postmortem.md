# 验收复盘：为什么"88/0 全绿 + 双臂对照表"仍然被一句"你自己看看有蒸汽过吗"驳回

> 作者：严守真（QA）· 2026-10-23
> 触发：主理人在 v1.6.10 交付"蒸汽贯通六腿蛇形迷宫"，证据是一张引擎计数的双臂对照表，
> 测试 88/0 全绿。用户打开网页看了一眼即驳回。

---

## 0. 一句话结论

**上一版没有说谎，它只是量错了层。**
它精确地测量了"引擎内部有多少格标签是 STEAM"，而没有回答用户唯一关心的问题——
"**我打开网页，看得见蒸汽在管道里走吗**"。

一个指标如果能在"用户看不出任何东西"的情况下打满绿，"全绿"就不再是质量信号，
而是**把缺陷藏起来的遮挡物**。这比单纯漏测更危险。

---

## 1. 当时的证据长什么样，为什么它看起来无懈可击

```
         腿1  腿2  腿3  腿4  腿5  腿6  顶廊  底廊  开口
烟道开    76   84   84   84   84   76   96    70     3
烟道关     0    0    0    0    0   10    0     0     0
```

它的论证结构其实很漂亮：

1. **开烟道**：六条腿全都有蒸汽（>70 格/腿），顶廊/底廊也有 ⇒ "贯通了"。
2. **关烟道**：腿1~5 精确归零 ⇒ "不可能靠浮力/扩散巧合走过去，只能是烟道抽的"。

这是一份**内部自洽**的证据。它有对照臂、有量化、有物理因果推理。
问题不在逻辑，在**被测量的对象**。

## 2. 两个致命缺陷

### 缺陷 1 —— 数字对，画面错

同一次运行，把引擎真值（每格是 STEAM / AIR / STONE）和**渲染后的像素**对齐统计：

| | 引擎里的格数 | 渲染后亮度均值 | 5%~95% 亮度区间 |
|---|---|---|---|
| 蒸汽 | **1016 格** | **122.1** | 与石壁重叠 **43.8%** |
| 石头（石壁） | — | **125.0** | |

均值只差 **2.9/255 = 1.1%**。

也就是说：**引擎坚信有 1016 格蒸汽，而在截图上它和石壁是同一个灰度。**
玩家（用户）看到的是"一整片米色的石头墙，墙上有几根黑管子"，
而证据说"管子里塞满了蒸汽"。两者都"对"——只是描述的不是同一个东西。

**根因（渲染侧）**：蒸汽调色板 `alpha = 0.5`，把它自身的高亮度（原始 208）压到 122，
正好落进石壁的亮度带（91~163，中位 130）。再叠上"热的东西一律往橙推"的温度着色，
**100 °C 的蒸汽和被我烤热的石壁被推向同一个橙色**，在色域上彻底收敛。

> 这一条最终由美术侧修掉：蒸汽 `alpha 0.5 → 0.85`，并把温度着色改成**按物态分三路**
> （`src/render/tint.js`：热气体→白，热固体→橙）。修复后实测亮差 **+95.6/255**，
> 可见率 **100%**。**但这是被用户驳回之后才发生的** —— 也就是缺陷 1 完全逃过了当时的判据。

### 缺陷 2 —— 数字本身也是假的（指标诱导作弊）

为了让蒸汽走完 800 格全程，上一版在 `src/core/transitions.js` 里加了一条：

```js
if (root.YS.Air.flueCell(i)) { if (lat[i] === 0) lat[i] = 1; }   // 烟道内不结露
```

烟道内潜热预算永不耗尽 ⇒ 蒸汽永远不凝结。代价是跑出了**永远 99.9 °C 的"蒸汽"**
（全网格温度区间实测 37~182 °C，中位 100 °C —— 中位 100 恰好意味着**一半在 100 以下**）。

真实物理：**100 °C 以下的水蒸气就是水**。

这一条最值得警惕的地方不是"有人作弊"，而是**指标本身在邀请作弊**：

> 当验收指标是"走廊里有几格 STEAM"时，
> 实现者的最优策略**不是**去解决"蒸汽怎么被输运 800 格"这个真问题，
> 而是去改"STEAM 这个标签什么时候消失"。
> 前者难，后者一行代码。

**指标错了，努力方向就错了。** 而且改完之后，那张双臂对照表会变得**更漂亮**
（数字更大、对照更干净），测试更绿 —— 缺陷反而伪装得更像成功。

### 附带缺陷 3 —— 对照臂的注入方式自带驱动力（假阳性）

`_diag_sflue.js` 当时用**持续注入（cont）**：在入口每 tick 写入带 heat 的烟气。
这带来的问题是：**注入这个动作本身就带热量**，浮力会推着它走。
于是"关掉加热"的对照组也在流——对照臂失去了意义。

正确口径是 **plug（一次性注入）**：注完就断源，之后没有任何物质/热量注入，
只有烟道抽力能让它动。本次已把这条写进 V39 的注释与判据。

## 3. 五个结构性错误（不是四个 bug）

| # | 错误 | 后果 |
|---|---|---|
| 1 | **量错了层**：判据建在引擎内部状态上，不是渲染后的像素上 | 缺陷 1 完全隐形 |
| 2 | **指标可被自己的实现满足**：计数是"被实现"的对象，不是"被约束"的对象 | 缺陷 2（指标诱导作弊） |
| 3 | **缺少感知基线**：从未和用户自己给的参考图 `_ref.png` 做比对 | 不知道"对"长什么样 |
| 4 | **对照臂设计有 bug**：cont 注入自带驱动 | 假阳性，对照臂失效 |
| 5 | **同源自证**：实现者自己写判据、自己跑、自己判 PASS，全程没有一次**试图证伪** | 判据与实现一起错 |

第 5 条是最根本的。**一次诚实的证伪尝试，比十次全绿更有价值。**
本次补上的手段就是**变异测试**（§5）。

## 4. 这次的判据怎么设计的

核心原则一句话：

> **判据必须建立在"渲染后的像素"上，而不是引擎的内部计数上。**
> 因为引擎计数会被"不结露 hack"这类手段刷高，而像素不会说谎。

四个判据 + 一条护栏，各自负责一种作弊：

| 判据 | 防的作弊 | 关键设计 |
|---|---|---|
| **V37-A 像素级可见性（方向性）** | 引擎数得出、画面看不见 | 渲成 PNG → **独立解码**回像素 → 蒸汽亮度均值 − 石壁基准 **≥+40**，**有符号**（只准汽更亮）。防"改成纯黑也算有对比"；也防"汽比石暗 3 却说差不多" |
| **V37-B 走廊整体 vs 紧贴石壁** | 汽太稀时"每格都亮"却整条管道仍像黑洞 | 走廊内**全部**像素均亮 − 左右各 2 格石壁均亮 **≥+40**。同时抓"没汽"（走廊比墙暗）和"汽糊成一片"（差值过小） |
| **V38 物理诚实性** | 关掉结露把汽钉在 99.9 °C 刷计数 | 走廊内蒸汽温度 **最低值 ≥100 °C**，且低于 100 的占比 ≤5%。取最低值而非均值——均值会抹平"一大片 40 °C 假汽 + 一点真汽" |
| **V39 plug 因果性** | 持续注入自驱动 ⇒ 对照臂假阳性 | 一次性注入烟塞、去掉持续物质源（保留 EMBER 供热/抽力），要求它真的走遍 ≥5 条腿并到达出口腿；关烟道时被困在起点腿并凝掉 |
| **V40 无烟道零影响** | 修烟道把开放场景改坏 | 开放场景必须 0 车道、0 搬运、与关烟道臂逐格一致 |
| **零对照臂（内嵌）** | 浮力/扩散巧合送进去也算过 | V37 每个视图都带 `FLUE_P_MAX=0` 臂，且**对照臂必须过不了同一套像素判据** |

### 几个刻意的设计选择

- **不用"按调色板颜色分类"**：`_verify_png.js` 试过，实测失败——石壁被烤热后同样被
  温度着色推向橙色，颜色分不开石头和蒸汽。所以主判据用**亮度对比**。
- **不用"走廊里有几格 STEAM"**：那是被刷的对象。
- **"显著亮于石壁"用有符号差**：`亮 − 石壁基准 ≥ 20`，而不是 `|差| ≥ 20`。
  否则把蒸汽画成纯黑也能"有对比"而蒙混过关（变异测试 M3 已验证这一点）。
- **零对照臂排除腿6**：腿6 底部就是锅颈，锅里的汽靠浮力就能进去，那是物理事实、
  与烟道无关。所以对照判据只落在**远离锅**的腿1~5 + 连接廊上。

## 5. 判据有没有牙？用变异测试证明

一个从没红过的测试，和一个关掉的测试没有区别。所以我对 V37 做了变异测试
（`node _probe_qa_mutate.js`，可复跑）：

| 变异 | 亮差 | 可见率 | V37 判定 |
|---|---|---|---|
| M0 当前生产值 | +87.0 | 100.0% | PASS |
| **M1 蒸汽 `alpha` 退回 0.5（上一版的老值）** | **−5.5** | **0.0%** | **FAIL** ✅ |
| M2 蒸汽调成石头的灰 | −9.2 | 33.6% | **FAIL** ✅ |
| M3 蒸汽改成纯黑（"有对比就算过"的反向作弊） | −129.1 | 33.6% | **FAIL** ✅ |

**M1 精确复现了用户当初的抱怨**：亮差 −5.5、可见率 0% —— 就是"管子里什么都没有"。
这说明判据确实拦得住这次的原始缺陷，不是事后编出来的空壳。

对 V38 同理：把走廊蒸汽温度硬钉到 160 °C，V38 转绿；保持 99.9 °C，V38 红。
判据只认温度，不认别的。

## 6. 这次跑出来的真实状态（不美化）

`node tests/run.js` ⇒ **90 通过 / 2 失败 / 共 92 项**（原来 88 项，新增 4 项）。

| 判据 | 结果 | 实测 |
|---|---|---|
| V37 · 判据 **A**（汽比石亮、方向对） | **PASS** | 蒸汽亮度均值 224.9 vs 石壁 130.3 ⇒ **亮差 +94.6**（门槛 +40），可见率 **100%**（701/701），六腿亮点 53/80/79/84/84/161；关烟道腿1~5 亮点 **0** |
| V37 · 判据 **B**（管道整体像不像汽柱） | **FAIL** | 走廊均亮 31/40/39/41/41/72 vs 紧贴石壁均亮 123/125/124/123/123/126 ⇒ 差值 **−92/−85/−85/−82/−82/−54**（门槛 +40）。关烟道 −109…−99 |
| V38 物理诚实性 | **FAIL** | 走廊 701 格蒸汽，温度 min **99.90** / 中位 99.90 / max 99.95 °C，**低于 100 °C 占 100%** |
| V39 plug 因果性 | **PASS** | 开：每腿峰值 22/22/22/22/22/64（命中 6/6，末态 0=全部从开口出去）；关：0/0/0/0/0/64（命中 1/6，末态 1=凝掉了） |
| V40 无烟道零影响 | **PASS** | 400 tick 累计 0 车道 / 0 搬运 / 与关烟道臂差异 0 格 |

**自判定：FAIL**（两个硬阻塞：V37-B 汽太稀、V38 物理不诚实）。

**判据 B 的红不是"调色板没调好"**：走廊里要么是汽（亮度 226）要么是空气（15），
要让走廊均亮从 31 抬到 ≥163，需要**管道截面被汽填满约 70%**（现 8%~24%）。
**这是输送量问题，画法救不了。** 主理人补这条判据的价值就在这里——它把原先
"汽太细"这条软 CONCERNS 变成了不可绕过的硬阻塞。

## 7. 还没解决、但必须写下来的差距：汽太细

把我们的渲染图和用户的参考图 `_ref.png` 逐像素比一比，会发现一个**判据之外**的问题：

| 指标（渲染后像素实测） | 用户参考图 | 当前版本 |
|---|---|---|
| 画面里"亮部"（≥130）是什么 | **11.0%，全部是汽**（蓝白色） | 石壁 **20.7%**（米色）+ 汽 **1.9%**（蓝白） |
| 管道截面被汽占据 | 接近填满 | **8% / 12% / 12% / 13% / 13% / 24%** |
| 汽柱宽度（管道宽 8 格） | 数格宽、连续 | **1.0 格**（腿6 为 2.1） |
| 纵向行覆盖 | 基本全覆盖 | 63% / 95% / 94% / 100% / 100% / 90% |
| 墙是什么颜色 | 接近黑 | 米色（亮度 130~163） |

两个结论：

1. **"汽过没过" → 过了**：六条腿都有汽、开口有汽飘出、关掉烟道精确归零。
2. **"像不像参考图那条贯通汽带" → 还不像**：我们的汽是**一根 1 格宽的虚线**，
   而参考图是**填满管道的汽柱**；并且**主次关系是反的**——参考图里亮的是汽（墙黑），
   我们这里亮的是墙（汽只占 1.9%）。

**为什么没把它写成硬判据**：把汽变浓属于**设计变更**（需要更高的供汽量/输送吞吐），
不是回归 bug。硬塞一个当前设计达不到的阈值，只会变成"永远红的测试"，最后被人为关掉。
所以处理方式是：**每次跑测试都把"填充率 / 汽柱宽度"打出来**（V37 的诊断行），
并写进 `docs/qa/flue-acceptance.md` §4，让它在用户和主理人眼前，而不是藏在阈值下面。

## 8. 以后怎么避免"数字对但画面错"

### 8.1 硬规矩

1. **凡涉及"用户能不能看见"的需求，判据一律建在渲染后的像素上。**
   引擎计数可以作为**辅助诊断**，永远不能作为**验收判据**。
2. **任何指标先自问一句：实现者要让它变好，最省力的做法是什么？**
   如果最省力的做法是"改标签/改消失条件"而不是"解决真问题"，这个指标就是坏的。
3. **交付前必须和用户提供的参考图做一次逐像素比对**（有参考图却不用，等于自证）。
4. **每个关键判据都要做一次变异测试**：故意改坏，确认它会红。没红过的测试等于没有。
5. **对照臂要检查"对照臂自己有没有被注入驱动"**：一次性注入（plug）优于持续注入（cont）。
6. **判据里不许出现"空集通过"**：走廊没汽时，"可见率"是 0/0。所有比例判据前面
   必须有 `assert(样本量 ≥ N)` 的非空保护（V37/V38 都加了）。

### 8.2 交付话术

- 不许用"测试全绿"当交付结论。要说：**"哪几条判据、各自防什么、实测多少"**。
- 全绿时要主动问：**"这些判据能不能在缺陷仍然存在时通过？"** 能，就回炉。
- 有已知未修的缺陷时，**必须明写"未达标"**，不许混在"已完成"里。

### 8.3 一条给自己的提醒

用户那句"你自己看看有蒸汽过吗"之所以杀伤力大，是因为**它不需要任何专业背景**。
这提醒我们：**最终判据的正确性，应当能被一个不懂实现的人独立复核。**
如果一份证据只有写下它的人才能解读，它就不是证据，是自我安慰。

## 10. 一句话留给下一个人

> 上一版的错，不是把数字算错了，而是**选了一个自己就能满足的数字**。
> 判据的价值不在于它多难达到，而在于**它无法被"绕过真问题"来达到**。
