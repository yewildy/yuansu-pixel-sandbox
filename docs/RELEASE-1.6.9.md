## 3. CHANGELOG 插入位置与写法

插入点：`CHANGELOG.md` **第 5 行**，即 `# Changelog` 标题 + Keep a Changelog 说明段之后、
原 `## [1.6.8] — 2026-10-18 01:25` 之前。1.6.8 及以下的历史条目**一字未改**。

结构（沿用 1.6.8 的体例）：

```
## [1.6.9] — 2026-10-19 03:06
   总述（含定理复习：为什么只剩两条出路）
   ### 新增 · 开口烟道贯穿流（src/core/air.js::flueFlow）
   ### 修复 · ★几何闸门 FLUE_WALL_FRAC（这一条不加就会打穿 1.6.8 的余量）
   ### 修复 · 车道数恒为 1 → 3
   ### 修正 · 抽力标定（FLUE_DRIVE_SCALE 8.0 → 4.0）
   ### 实测
   ### 已知限制（如实记录，不是 bug）
   ### 测试
```

**写法原则：讲"为什么"，不只列"改了什么"。** 三处着重写了因果链：

1. **定理先行** —— 先复述"任意割集净通量恒等于 0 ⇒ 每格独立掷骰的定向输运期望值一律为 0"，
   再说明因此只剩两条出路（闭合环一步 / 开口边界不守恒），`flueFlow` 走第二条。
   不写这条，读者只会看到"又加了一个机制"，看不出为什么不能沿用老办法。
2. **为什么必须加 `FLUE_WALL_FRAC`** —— 写清了失败的具体路径（羽流被误判 → 锅上方架起 776 格
   隐形输送带 → V25 余水 127 → 110 → 跌破 30% 门槛），以及为什么数"刚性壁"而不是"非气体"
   （锅里正下着冷凝水滴雨，水也是非气体，以水为壁羽流照样过闸）。
3. **已知限制照实写** —— 5 条，包括"半开放凹槽式烟道会被漏掉""热源在中段不驱动"
   "车道只覆盖 1/3 截面""SMOKE 衰减造成质心回落观感""概率闸门导致脉冲式推进"。

## 7. 异常与处置

### 异常 1（已修复）：首次推送的提交信息用了默认文案

- **现象**：第 1 次提交落地的 message 是 `chore: 同步 全部（164 个文件）`，
  而不是 `msg-1.6.9.txt` 里的完整说明。
- **根因**：`push.js` 的参数解析是 `process.argv.indexOf('--msgfile')` 取**下一个 argv**，
  即要求 `--msgfile <路径>`（空格分隔）。我传的是 `--msgfile=msg-1.6.9.txt`（等号形式），
  `indexOf` 匹配不到 ⇒ `CUSTOM_MSG = null` ⇒ 落到 `chore: 同步 ${label}（${n} 个文件）` 兜底。
- **影响面**：**仅提交信息**。**文件内容完全正确**（已由 §6.2 的四条 curl 核对证实）。
- **处置**：以 `01c960d7`（推送前的 main）为父提交，用**同一份本地树**（外加本发布报告）
  重建提交、改用完整说明，再 PATCH `refs/heads/main`。树内容等价 + 多了发布报告 ⇒
  无内容丢失风险；被替换的提交对象仍在仓库对象库里，可回溯。
- **教训（写给下次）**：`push.js` 的 `--msg` / `--msgfile` **只认空格分隔**，不认等号形式。

### 异常 2（无需处置，记录）：远端多出一个文件

`tests/_t63_evidence.js` 在远端存在、本地不存在（本地过滤规则更严）。

## 9. 回滚预案

本版是**纯前端静态站点 + GitHub Pages**，无服务端、无数据库，回滚成本极低：

1. **代码回滚**：把 `src/core/air.js` / `src/core/balance.js` 还原到 1.6.8 版本后重跑 `push.js`；
   或直接用 `RepoBuilder.updateRef(sha, force=true)` 把 `main` 指回 `01c960d7`（1.6.8 的 main）。
   注意同步把 `src/main.js` 的版本号与 `index.html` 的缓存串改回，否则玩家会拿到
   "写着 1.6.8 却是 1.6.9 代码"的混合态。
2. **只关机制、不回滚代码**（更轻）：把 `AIR.FLUE_P_MAX` 设为 0 ⇒ `flueFlow` 整个关闭并清理状态。
   这是四臂对照里的 `off` 臂，已实测全 0 输运、V25 回到 127 ⇒ **这条路径是被验证过的**。
3. **热修流程**：改完 → `node --check` 全量 → `node tests/run.js` 必须 87/0 →
   `push.js --dry` 预演 → 真推 → 等 60~90 秒 → curl 四条核对。
   **字符串冻结后不再改字符串**（本项目当前无 i18n 字符串改动，该约束本版未触发）。

## 10. 下一步建议

1. **补一条自动化回归用例**（消 R1）：把 S 形烟道场景缩减到能在 20~30 秒内跑完的规模
   （例如 120×80、观测 600 tick），只断言两个硬指标 —— 「出口窗到达 > 0」与
   「`off` 对照臂出口窗 = 0」。这两条一旦挂了就说明机制被打破，值得进每次都跑的套件。
2. **给 V25 余量做长期处置**（消 R3）：32% vs 30% 只剩 2 个点，等于没有缓冲。
   建议单独开一个任务研究"锅内蒸发是否偏快"，而不是继续靠 `FLUE_WALL_FRAC` 这类几何闸门兜底。
3. **把 `FLUE_WALL_FRAC` 从经验门槛升级为可解释判据**（消 R2）：当前 0.8 是"实测落在空隙里"。
   更稳的方向是判"洞口是否比通道主体明显更开放"（相对量），而不是绝对占比。
4. **发布节奏**：本版从 1.6.8 到 1.6.9 隔了 1 天，且 1.6.4~1.6.8 曾积压 5 个版本未推
   （用户明确抱怨过"没有推送"）。建议**每个版本完成即推**，别再攒。
