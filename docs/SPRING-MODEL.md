# 水源泉 / 克隆体：持续产出 + 活体上限（v1.6.1）

> 真源文档 · 关联：`src/core/balance.js`（`SPRING` / `CLONE` 组）、`src/core/reactions.js`（R19 / R14）、
> `tests/run.js`（12a / 12b / V26 / V32）。
> 背景：用户实测反馈「还有水源泉等方块，只会给一会儿水，根本不持久。」

---

## 1. 问题：累计配额把「持续水源」退化成了「一次性定量水源」

旧模型（v1.1.0 起）给水源泉 / 克隆体设了一道**全局累计配额**：

```js
var CLONE  = { COPY_INTERVAL: 4, MAX_CELLS: 2000 };
var SPRING = { EMIT_INTERVAL: 6, MAX_CELLS: 1500 };
```

```js
if (ctx.springCreated >= Balance.SPRING.MAX_CELLS) continue;   // 累计产满 → 永久停喷
```

`MAX_CELLS` 统计的是**整个生命周期里累计产出的格数**，一旦写满就**永久**停喷。
单水源泉每 6 tick 产 1 格水，约 `1500 × 6 = 9000 tick`（≈2.5 分钟）就到顶，
此后无论玩家怎么玩、把水排掉多少，水源泉都**再不出水**。

当年设这道闸门是为了「防无限造水把世界灌满」，但它用错了计量口径：
真正要防的是「**世界当前被灌满**」，而不是「**历史上累计产了多少**」。
于是一个本应"取之不尽"的水源，变成了"给一会儿就死"的一次性水龙头 —— 正是用户反馈的现象。

---

## 2. 新模型：生命周期无限 + 速率受限 + 活体上限

```
只要 SPRING / CLONE 自身还在场景里 → 持续产出（仅受 EMIT_INTERVAL / COPY_INTERVAL 节流）
防"灌满世界"  →  改用「活体上限 LIVE_MAX」：达到上限时**暂停**，降回阈值以下**自动恢复**
```

| 机制 | 旧（累计配额） | 新（活体上限） |
|---|---|---|
| 计量对象 | 生命周期累计产出格数 | **当前世界里**该产物的格数 |
| 达到阈值 | **永久停喷** | **暂停**（降回后自动恢复） |
| 观感 | 一次性定量水源 | 持续水源（可被"排空"重新激活） |

### 2.1 活体上限的取值

```js
var CLONE  = { COPY_INTERVAL: 4, LIVE_MAX: 5000 };
var SPRING = { EMIT_INTERVAL: 6, LIVE_MAX: 6000 };
```

- `SPRING.LIVE_MAX = 6000`：产物是 `WATER`，直接统计世界里 `WATER` 格数。
  画布 320×180 = 57600 格，6000 格水约占 10% 面积 —— 足够"看得见地出水"，
  又不会在 95% 填充场景下把 tick 预算压爆（实测见 §4）。
- `CLONE.LIVE_MAX = 5000`：克隆体的产物是**任意可移动元素**，无法廉价追踪"哪些格是克隆产物"，
  故用**全体可移动（`movable` 且非 AIR）格数**作为活体计数的**保守上界**（宁可早停也不让世界被灌满）。

### 2.2 低频节流统计（性能）

活体计数**不每 tick 全网格扫描**，而是：

- 每 `LIVE_SCAN_INTERVAL = 30 tick` 扫一次全网格，缓存 `liveWaterCount` / `liveMovableCount`；
- 两次扫描之间，**产出时本地即时 +1**（`liveWaterCount++` / `liveMovableCount++`），
  以保证在水/产物两次扫描之间**也不会越过 LIVE_MAX**（**SPRING 自身喷发的**严格上界，口径见 §5）；
- tick 回退（新建引擎 / `engine.clear()` 后 tick 归 0）时强制重扫，避免跨引擎沿用陈旧缓存。

净效果：每 tick 成本 ≈ 0（仅每 30 tick 一次 O(n) 扫描），且上限严格不被越过。
计数**不消耗 RNG、不改任何物理状态**，故不影响确定性（测试 5 / N1-10 哈希不变）。

### 2.3 兼容性

- `engine.springCreated` / `engine.cloneCreated` **保留**为**累计统计**（跨 tick 累加，只增不减），
  仅用于观测 / HUD / 测试，不再参与"是否停喷"的判定。
- `MAX_CELLS` 字段已**删除**（`SPRING.MAX_CELLS === undefined`，见测试 8b）。
- 存档格式不变（活体计数是运行时派生量，不序列化）。

## 3. 其它"一次性配额"排查

`grep -rn MAX_CELLS src/` 后确认：仅 `SPRING` / `CLONE` 使用过累计配额，已一并改为 `LIVE_MAX`。
其余带上限的常量都是**活体 / 每 tick / 每次事件**口径，**不是**累计配额，语义正确，保持不动：

| 常量 | 口径 | 说明 |
|---|---|---|
| `FIRE.MAX_BURN_CELLS = 8000` | 当前 FIRE 格数（活体） | 每 tick 惰性重计，天然可恢复 |
| `AIR.MAX_MOVE_BUDGET = 12000` | 每 tick 移动预算 | 逐 tick 重置 |
| `TNT.CHAIN_MAX = 12` | 单次爆炸链深 | 每次爆炸重置 |
| `P.MAX_EXPLOSION_CELLS = 2000` | 单次爆炸处理格数 | 每次爆炸重置 |
| `SEED.CHAIN_MAX` / `PLANT.MAX_COLONY` | 结构规模 | 非"产出配额" |

## 4. 实测数据（本机 Node / V8）

测试 `tests/run.js` V26：64×64 画布、单水源泉置于顶部 `(32,1)`、跑 20000 tick。

| 指标 | 实测 |
|---|---|
| 总耗时 | **≈ 11.4 s**（20000 tick） |
| 分窗口产出（每 4000 tick） | **666 / 667 / 667 / 666 / 667**（5 个窗口全部 > 0） |
| 累计 `springCreated` | 3333 |
| 末态 `WATER` | 3333（≤ `LIVE_MAX=6000` ✓） |

对照：旧模型下同一场景在第 3 个窗口（tick 8000–12000）就已归 0
（累计 1500 格在 ≈9000 tick 产满即永久停喷），窗口 4/5 必为 0 —— V26 正是这点的回归护栏。

测试 12b（活体上限本身）：120×80 画布、预填 6000 格水、顶部单水源泉。

| 阶段 | 实测 |
|---|---|
| 满水 70 tick | `springCreated = 0`（暂停）、`WATER = 6000` |
| 排掉 300 格水后 300 tick | `springCreated` 恢复到 46（自动恢复 ✓）、`WATER = 5746 ≤ 6000`（本场景仅 SPRING 一处水源）✓ |

测试 V32（**世界级口径**，`tests/run.js`）：120×80 画布、预填 6000 格水使泉暂停、
再注入 80 格 60°C 高温冰（**非 SPRING 水源**）。

| 指标 | 实测 |
|---|---|
| 融冰后 `WATER` 峰值 | **6080（> 6000 ✓）** —— 证明非 SPRING 水源不被喷发闸门约束 |
| 期间 SPRING 自身新增 | **0**（泉全程暂停 ✓） |
| 排掉 300 格水后 300 tick | SPRING 恢复喷发，新增 **+≈49**（自动恢复 ✓） |
| 本测试耗时 | ≈1 s（本机实测 0.95–1.07 s；短窗口：注入后仅跑 200 tick） |

> 12b 与 V32 的口径差异：12b 只验证「**SPRING 自身喷发**不越界 + 排空后恢复」；V32 额外验证
> 「**非 SPRING 水源**可以令 `WATER` 超过 `LIVE_MAX`，但会让 SPRING 暂停更久、排空后恢复」。

## 5. 已知取舍 / 局限

- **护栏口径要精确：`LIVE_MAX` 约束的是「SPRING 自身喷发」，不是「世界级 `WATER` 硬上限」。**
  - **SPRING 自身喷发不会使 `WATER` 超过 `LIVE_MAX`**：产水时本地即时 `liveWaterCount++` 且先判上限，
    QA 实测（`_qa_f1.js` F1-A）满水时暂停、喷发那一瞬的 `WATER` 峰值为 0 / 5746，从不越界。
  - **融冰 / 融雪 / 蒸汽冷凝等其它水源不受这道闸门约束**（ICE→WATER 等是物理相变，节流它们等于篡改物理）。
    它们产出后会在下一次（≤30 tick）低频扫描时被计入 `liveWaterCount`，从而**让 SPRING 暂停更久**
    —— QA 实测（`_qa_f1.js` F1-B）：预填满 6000 水后注入 80 格 60°C 高温冰，`WATER` 达峰值
    **6080 > 6000**，而**同期 SPRING 自身新增 = 0**；把这些水排空到阈值以下后，SPRING 自动恢复喷发
    （回归护栏：`tests/run.js` V32）。
  - 即：**"SPRING 喷发不越界"成立，"世界级 `WATER` 硬上限"不成立**。后者不是本机制的目标；
    若日后确需世界硬上限，应把"非 SPRING 产水"也计入计数（成本与复杂度另议）。
- `CLONE` 的活体计数用"全体可移动格数"作保守上界 —— 若世界里本来就有大量无关液体/气体，
  克隆体会**偏早**暂停。这是"宁可早停也不灌满"的刻意取舍；若日后需要精确追踪产物来源，
  应为格子增加 provenance 位（成本与复杂度另议）。
- 活体计数有 ≤30 tick 的滞后（扫描间隔），但产出时的本地即时 +1 已保证**SPRING 自身喷发不越过上限**；
  只有"世界里有东西被移除"（下水/被玩家擦除）需要等下一次扫描才被感知 → 恢复产出最多滞后 30 tick。
- 上限是**产物总量**护栏，不是"每一处水源都无限"。世界里水一旦到 6000 格且不再减少，
  所有水源泉都会保持暂停 —— 这是**活的**暂停：排掉一些水即自动恢复。
